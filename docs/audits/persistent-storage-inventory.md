# Persistent storage inventory

Audited application source against main `ca35fd1` (PR #22). No active fitness-data key was missing from the existing backup allowlist. The gaps were future-source detection, completeness attestation, and clear rejection of some IndexedDB read errors. No new storage mechanism was discovered.

There are **83 registered sources**: **77 localStorage keys/patterns included**, **one included IndexedDB database/store**, and **five intentional exclusions** (two temporary localStorage keys, one sessionStorage flag, two CacheStorage sources). Patterns represent arbitrarily many dated records, not one record. Some included exact keys exist solely for compatibility, not active features. A registry source is different from an individual call site or record count.

The table traces actual TypeScript/JavaScript AST calls, imported constants, finite maps and dynamic expressions. File operations indicate read/write locations; generic guarded export/restore loops are described below. Run `npm run audit:storage -- --json` for individual locations and `npm run audit:storage -- --write-inventory` to refresh the table after a reviewed registry change.

## Boundaries and findings

- `workout-tracker-data` holds workout definitions, historical logs, routines and journals; `workout-tracker-logs` preserves older history separately. Workout duration includes the persisted current session as well as completed sessions.
- Food Tracker uses both `fitcircle_food_YYYY-MM-DD` and `fitcircle_food_trackerYYYY-MM-DD`. Current food database contains built-ins, custom foods and edits. Removing an entry encodes its deletion by absence; the legacy built-in deletion-ID list is separately preserved.
- `FitCircleCustomFoods/foods` is the only production IndexedDB store. The local food service reads it during its existing migration. Export explicitly reads it, too. Restore merges its records into `fitcircle_food_database`; current localStorage values win ID collisions. Legacy-only IDs still merge, including stale legacy records without deletion tombstones. This existing compatibility behavior is unchanged. Foods may be normalized/reordered; restore sets the existing migration flag to `true`. Restore does not rewrite/delete the legacy database. Existing empty legacy-schema initialization on first open remains unchanged.
- Every included localStorage source is read by the guarded `createBackup` enumerator and written by validated `applyRestore` in `client/src/lib/backup.ts`. Rollback/recovery loops only operate on validated plan/journal keys. Generic `createStorageHook` operations are exempted internally, but each feature call to that helper is audited. These exact loops, including operation counts, are reviewed in `scripts/lib/storage-boundaries.ts`.
- Food history enumeration reads the `fitcircle_food_` prefix and skips non-array values. Settings' existing user-confirmed erase routine filters recognized app keys. The audit adds no erase operation. `scripts/export-legacy-backup.js` is the separately invoked Replit console migration reader, not the main exporter; it reads its historical prefix selection and explicit food store. Its missing-store handling differs from the current strict exporter.
- CacheStorage `fitcircle-release-receipts-v1` holds verified public application release metadata, never personal fitness data. It is intentionally excluded from export/restore.
- CacheStorage `fitcircle-pages-*` contains static offline resources from `scripts/sw-template.js`; no user records. Cache behavior is unchanged. Other apps' origin keys/caches are neither included nor modified by backup/restore.
- Reminder insertion cursor, one-shot dashboard-return session flag and in-flight restore journal are deliberately excluded. Export refuses an outstanding restore journal, preserving startup recovery rather than exporting partial state.
- No OPFS, WebSQL, cookie-based user data, persistence wrappers or additional databases were found. Active meditation/fasting timer state held only in React memory is not a persistent source. Food search index is derived in memory.
- Scope: all client TS/TSX/JS/JSX and inline HTML scripts, shipped worker template, and manual legacy exporter. Build/tooling scripts and tests manipulate isolated synthetic browsers rather than production user records. Build-generated static caches are represented by their template. Dynamic code loading or future custom persistence wrappers require audit support; this is static source analysis, not proof about arbitrary code outside the repository.
