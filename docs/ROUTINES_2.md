# Routines 2.0

Routines configure training. Home performs and logs it. No programs, equipment brands, recommendations, automatic periodization, or logging controls are bundled into the planner.

## Data and identity

`workout-tracker-data` remains the sole workout document. Reusable definitions keep their IDs, colors, legacy schedule metadata and optional equipment, notes, weight in pounds and rest in seconds. New definitions carry a prescription (`targetType`, `sets`, `perSet`); `dailyGoal` remains its computed total and `setsGoal` its set count for existing readers. Duration targets and totals use **seconds**, never repetitions. Zero external weight is valid; arbitrary resistance levels belong in notes.

Each routine stores ordered `placements`: stable placement ID, exercise ID, prescription, optional pounds/rest. Removing or moving a placement changes only that routine. Weekdays belong to the routine, so changing them does not rewrite definitions. A definition can be reused in multiple routines; distinct placements retain separate identities even when they reference the same definition. Unassigned definitions remain available through Add Exercise within routines, but have no independent schedule.

Home has **one daily logging identity per exercise placement**. Scheduled routines are ordered by creation timestamp and then ID; placements keep their saved order within each routine. Reusing a definition produces separate circles, targets and progress for each placement, labeled with its routine. New records use `placement:` followed by the JSON-encoded routine/placement ID pair, and snapshot the exercise, routine and placement IDs alongside the existing goal/name/color/unit metadata. Individual-exercise statistics aggregate these records by definition ID without mixing seconds into repetitions.

During legacy conversion, one deterministic placement per definition (first routine in the order above, then first placement) retains that definition's original logging ID through `legacyLogId`. This preserves existing completion and Undo without copying shared legacy activity into several new placements. Other placements use separate identities. Removing the canonical placement does not reassign its old log ID to a different placement; recorded activity remains readable by its snapshots.

The first daily action snapshots the goal, set count, target unit, name, color, routine name and placement identity. Later schedule and prescription changes do not replace that snapshot; the new prescription applies to future unlogged days. Undo and historical editing use the snapshot. Duration circles credit a completed set of prescribed seconds with each tap; they do not measure elapsed time or auto-run the Home timer. The separate workout session and timer controls are unchanged.

Training variations are retired. An active legacy variation is materialized into the standard placement prescriptions and rest values on read, and its active ID is cleared. The projection is idempotent, preserves placement/logging IDs and leaves definitions and activity untouched. Inactive variation metadata remains accepted in old backups, but has no controls or live switching behavior. No separate migration key or version bump is introduced.

## Legacy migration and durability

Migration is a pure, idempotent read projection. For each routine lacking `placements`, include all definitions whose standalone weekdays overlap the routine weekdays; an empty/missing exercise schedule means daily. Sort by exercise ID and use `legacy:<routine ID>:<exercise ID>` placement IDs. An existing placements array, including an empty one, is authoritative. This matches the previous Routines overlap presentation rather than interpreting the dormant `routineId` field as membership.

Definitions, colors, weights, journals, dates and daily logs are not changed by this migration. Accepted legacy array definition containers become an ID-keyed map; duplicate IDs cause safe recovery rather than overwriting definitions. Before the first scheduling conversion, any definitions still unassigned are grouped by their exact former weekday schedule into ordinary “Imported workouts” routines (missing/empty legacy weekdays mean daily). IDs and placement order are deterministic; original definitions and logs are retained. The optional `routineSchedulingVersion: 1` marker prevents removed routines/placements from being recreated and prevents newly unassigned definitions from scheduling themselves. Schedule metadata is read only during this compatibility conversion; live scheduling uses routine weekdays exclusively. No exercise editor exposes weekday or time controls.

The complete projected document is written only by the next successful explicit mutation (or the existing midnight count reset). Reads never write partially migrated data. Older backups without the marker undergo the same pure conversion after import. Updated backups retain the optional marker, compatibility IDs and placement snapshots; no storage keys or backup container formats change. The shared store validates the entire next document and performs one localStorage write; failed writes leave the durable original and visible draft intact.

For evenly divisible legacy targets, `sets × perSet` equals the old total. Uneven totals retain an explicit `legacyTotal`, shown as a legacy split: 20 reps / 3 sets still credits 6, 7 and 7 reps, totaling exactly 20. No stored log is rounded. Changing sets or per-set targets explicitly replaces that split. On a definition target edit, unsnapshotted numeric legacy logs are wrapped with their previous goal and repetition unit so later edits cannot reinterpret them; recorded amounts stay exact.

Backup validation accepts legacy and planned forms, archived definitions, placement order, optional details, variations and typed snapshots. Existing backup/import/export formats and keys are unchanged. Exported raw records remain byte-exact; migration occurs when restored data is read, and is durably committed atomically with a subsequent mutation.

## Deletion and historical consumers

- Remove placement: only the routine draft changes; Save commits it. Definitions and logs stay intact.
- Delete routine: confirmation required; shared definitions and all history stay intact.
- Delete definition: confirmation required; remove active placements and archive the definition under `archivedWorkouts`. Keep daily logs. Archived exercises do not appear as Home circles or exercise choices.
- Historical activity edits remain separate operations. This planner does not delete historical activity.

Home, Calendar, Dynamic Overview and Recent Activity use the shared projection/progress helpers. Calendar and all-time/monthly/individual statistics exclude typed seconds from repetition totals. Current-day statistics and totals include already-recorded activity even when its definition is archived or its routine schedule changes. Home circles themselves show only currently scheduled routine placements. Duration remains visible separately in historical detail, Recent Activity and workout statistics. Recovery completion uses set/goal snapshots. Journal consumers keep their existing shared-store behavior. Profile training summaries use the shared statistics calculation. Legacy untyped logs always mean repetitions, even if a definition later becomes duration based. Historical consumers resolve dated logging identities, including deleted or rescheduled placements, rather than filtering records by current exercise schedules. Metadata already destroyed by an older version cannot be recovered; any unmatched raw log entries remain untouched.

## Verification and limits

Focused coverage lives in `routine-planning.test.ts`, `routines-v2.spec.ts` and the existing workout, initialization, backup, routing and configuration regressions. It exercises overlap migration/idempotence, uneven totals, independent shared placements, routine rescheduling and stable legacy logging identity, legacy variation retirement, archival, separate units, old/new backup round trips, routed draft handoffs, Home sets/undo and mobile layouts. Physical iPhone behavior is not inferred from browser viewport checks.

Within an unsaved routine, Save Exercise explicitly saves a reusable definition. If its parent routine draft is later canceled, the definition remains available through Add Exercise; the uncommitted placement is discarded. No training data is silently deleted to undo an explicitly saved definition.

## Exercise catalog and routine controls

The FitCircle header is shared with Home. My Routines has no summary or instructional lines. Add Exercise navigates directly to `/routines/exercises/add?routine=…`, retaining an unsaved parent routine draft when necessary. Search, body-part chips and All/Bodyweight/Equipment filters operate locally over 209 bundled templates and reusable custom definitions. The original curated text dataset has 13 categories, deterministic catalog IDs, equipment, aliases and suggested target units; it has no sets, repetitions, weights, schedules, images, external APIs or network search. Viewing it never populates workout storage.

Selecting a bundled template prepares the existing routed configuration form. Targets start blank and must be supplied by the user. A `catalogId` links a configured reusable definition back to its bundled starting template; selecting it for another routine reuses that identity but creates a separate placement with its own targets and metadata. The catalog template is never edited or written to user storage. Existing definitions are treated as user-created exercises and retain their IDs.

The + Custom action opens `/routines/exercises/custom/new`; custom definition management uses `/routines/exercises/custom/edit?id=…`. Custom definitions and their category live in the existing workout document and backup format. Catalog rows configure a new placement; a separate pencil action edits the reusable custom template. Name, color, equipment, notes, category, weight and rest are saved as placement overrides so editing one placement does not update another. Template edits materialize any inherited details on existing placements before changing template defaults. Explicit null weight/rest overrides mean no external weight/rest, preserving that choice across later template edits.

Removing a custom template from the catalog asks for confirmation with its routine usage count and sets `catalogHidden`; saved placements and history remain intact. Removing a placement still affects only that routine. The existing, separately confirmed Home definition-archive operation remains available. These actions have distinct meanings.

Catalog search state is transient. Selecting/configuring then saving returns to the originating routine, skipping the catalog. Cancel returns to the catalog and preserves filters. Custom template edits return to the catalog; Back returns to the parent routine. Home’s existing Edit action opens the same placement editor with a return-to-Home destination, so it edits the displayed placement instead of changing a shared default. Its confirmed Delete action removes that placement while retaining the reusable definition and recorded activity. Persisted routes can be refreshed; invalid IDs use the existing safe fallback. Definition and placement creation from a saved routine share one validated atomic write. Within an unsaved routine, Save Exercise explicitly saves a reusable definition while the placement stays in the routine draft until Save Routine; canceling the routine never deletes that definition.

Drag only the six-dot handle to reorder within a routine; touch/pointer capture suppresses ordinary scrolling during the gesture, with controlled edge scrolling for long lists. The raised row and insertion line show the pending move. Release commits; Escape or pointer cancellation discards it. Focus a handle and press Arrow Up/Down for keyboard reordering, announced by a live region. Main-card moves save immediately through the existing validated routine operation. Editor moves remain a draft until Save Routine; Cancel keeps the stored order unchanged.
